# Flutter UI Engineering

## Overview

Build production-quality Flutter interfaces that are accessible, performant, and visually polished. The goal is UI that looks like it was built by a design-aware engineer at a top company — not like it was generated by an AI or copied from the `flutter create` template. This means real design system adherence, proper accessibility, platform-appropriate interaction patterns, and no generic "AI aesthetic."

## When to Use

- Building new screens or widgets
- Modifying existing user-facing interfaces
- Implementing adaptive layouts (phones, tablets, foldables, landscape, large text)
- Adding interactivity, navigation, or state management
- Fixing visual or UX issues

## Widget Architecture

### File Structure

Organize by feature, and colocate everything related to it:

```
lib/features/tasks/
  cubit/
    tasks_cubit.dart        # Cubit
    tasks_state.dart        # State (part of tasks_cubit.dart)
  view/
    tasks_page.dart         # Page: provides the Cubit (BlocProvider)
    tasks_view.dart         # View: consumes the Cubit (BlocBuilder)
  widgets/
    task_item.dart          # Widgets private to this feature
  data/                     # Models, repository interface (if not shared)
test/features/tasks/
  cubit/tasks_cubit_test.dart
  view/tasks_view_test.dart
  widgets/task_item_test.dart   # Widget and golden tests
```

The Page/View split keeps `BlocProvider` creation in the Page and the UI in the View, so the View can be tested by providing a mock Cubit.

### Widget Patterns

**Prefer composition over configuration:**

```dart
// Good: Composable
AppCard(
  child: Column(
    children: [
      const AppCardHeader(title: 'Tasks'),
      TaskList(tasks: tasks),
    ],
  ),
)

// Avoid: Over-configured
AppCard(
  title: 'Tasks',
  headerVariant: HeaderVariant.large,
  bodyPadding: Spacing.md,
  content: TaskList(tasks: tasks),
)
```

**Keep widgets focused, and make them `const` when possible:**

```dart
// Good: Does one thing
class TaskItem extends StatelessWidget {
  const TaskItem({
    required this.task,
    required this.onToggle,
    required this.onDelete,
    super.key,
  });

  final Task task;
  final ValueChanged<String> onToggle;
  final ValueChanged<String> onDelete;

  @override
  Widget build(BuildContext context) {
    final theme = Theme.of(context);
    return ListTile(
      leading: Checkbox(
        value: task.done,
        onChanged: (_) => onToggle(task.id),
      ),
      title: Text(
        task.title,
        style: task.done
            ? theme.textTheme.bodyLarge?.copyWith(
                decoration: TextDecoration.lineThrough,
                color: theme.colorScheme.onSurfaceVariant,
              )
            : theme.textTheme.bodyLarge,
      ),
      trailing: IconButton(
        tooltip: 'Delete ${task.title}',
        icon: const Icon(Icons.delete_outline),
        onPressed: () => onDelete(task.id),
      ),
    );
  }
}
```

**Extract widgets into classes, not `_buildX()` methods.** A helper method returning a `Widget` cannot be `const`, rebuilds with its parent, and cannot be tested or reused on its own. A small widget class can.

```dart
// Avoid
Widget _buildHeader() => Padding(/* ... */);

// Prefer
class _Header extends StatelessWidget {
  const _Header();
  @override
  Widget build(BuildContext context) => const Padding(/* ... */);
}
```

**Separate data fetching from presentation** (Page provides, View renders):

```dart
// Page: creates and provides the Cubit
class TasksPage extends StatelessWidget {
  const TasksPage({super.key});

  @override
  Widget build(BuildContext context) {
    return BlocProvider(
      create: (context) => TasksCubit(context.read<TasksRepository>())..load(),
      child: const TasksView(),
    );
  }
}

// View: renders every state, exhaustively
class TasksView extends StatelessWidget {
  const TasksView({super.key});

  @override
  Widget build(BuildContext context) {
    return BlocBuilder<TasksCubit, TasksState>(
      builder: (context, state) => switch (state) {
        TasksLoading() => const TaskListSkeleton(),
        TasksFailure() => ErrorState(
            message: 'Failed to load tasks',
            onRetry: context.read<TasksCubit>().load,
          ),
        TasksLoaded(:final tasks) when tasks.isEmpty =>
          const EmptyState(message: 'No tasks yet'),
        TasksLoaded(:final tasks) => TaskList(tasks: tasks),
      },
    );
  }
}
```

## State Management

**Choose the simplest approach that works:**

```
StatefulWidget / ValueNotifier     → Ephemeral UI state (animation, focus, tab index, text input)
Lifted state                       → Shared between 2-3 sibling widgets
InheritedWidget / Theme / Locale   → Theme, locale (read-heavy, write-rare)
Cubit (BlocProvider)               → Feature state: the default for anything with logic or async work
Bloc                               → Event-driven flows that need transformers (debounce, droppable), or an auditable event log
Route state (go_router params)     → Filters, pagination, deep-linkable UI state
HydratedBloc / persistent storage  → State that must survive app restarts
```

**Cubit by default, Bloc when events earn their keep.** Cubits are less ceremony: methods that `emit` states. Move to Bloc when you need event transformers (search-as-you-type debounce, ignoring duplicate submits) or when tracing "what happened" matters.

**Rules for Cubit/Bloc state:**
- States are **immutable** and implement value equality (`Equatable` or equivalent). Without it, every `emit` looks like a change and rebuilds listeners.
- Model states as a `sealed` class hierarchy (or one class with a status enum) so the UI must handle loading, failure, empty, and loaded exhaustively.
- Never hold a `BuildContext` in a Cubit, and never call one Cubit from another. Coordinate through the presentation layer (`BlocListener`) or a shared repository stream.
- Use `context.read` in callbacks and `BlocBuilder` / `BlocSelector` / `context.watch` in `build`. Never `watch` inside callbacks.
- Use `BlocListener` (not `BlocBuilder`) for side effects: navigation, snackbars, dialogs.
- Narrow rebuilds with `buildWhen` or `BlocSelector` when the state is large.
- Provide a Cubit as low in the tree as the widgets that need it. App-wide only for genuinely app-wide state (auth, theme, locale).
- Close what you own: cancel stream subscriptions and timers in the Cubit's `close()`.

**Avoid prop drilling deeper than 3 levels.** If you're passing parameters through widgets that don't use them, provide the value with `BlocProvider` / `RepositoryProvider` or restructure the tree.

## Navigation

Use one router for the whole app (for example `go_router`) rather than mixing imperative `Navigator.push` calls with declarative routes.

- Define routes and their paths in one place; prefer typed routes so parameters are checked at compile time.
- Pass **IDs, not objects**, between routes. The destination screen loads its own data, which also makes deep links work.
- Handle deep links and redirects (for example an unauthenticated user) in the router's `redirect`, not inside screens.
- Use `context.go` to replace the stack for top-level destinations, `context.push` for drill-down.
- Intercept back navigation with `PopScope`, not the deprecated `WillPopScope`. Keep Android's system back and iOS's swipe-back working; do not disable them without a reason.
- Never use a `BuildContext` across an `await` without checking `context.mounted` first.

## Design System Adherence

### Avoid the AI Aesthetic

AI-generated UI has recognizable patterns. Avoid all of them:

| AI Default | Why It Is a Problem | Production Quality |
|---|---|---|
| `ColorScheme.fromSeed(seedColor: Colors.deepPurple)` | It is the `flutter create` template default; every app ends up looking identical | Use the project's actual brand color scheme |
| Excessive gradients | Gradients add visual noise and clash with most design systems | Flat or subtle gradients matching the design system |
| `BorderRadius.circular(24)` on everything | Maximum rounding ignores the hierarchy of corner radii in real designs | Consistent radii from the design system's shape tokens |
| Generic hero sections | Template-driven layout with no connection to the actual content or user need | Content-first layouts |
| Lorem ipsum-style copy | Placeholder text hides layout problems that real content reveals (length, wrapping, overflow) | Realistic placeholder content, including long strings |
| Oversized padding everywhere | Equal generous padding destroys visual hierarchy and wastes screen space, especially on small phones | Consistent spacing scale |
| Stock card grids | Uniform grids are a layout shortcut that ignores information priority and scanning patterns | Purpose-driven layouts |
| Shadow- and elevation-heavy design | Layered shadows and blurs add depth that competes with content and cost raster time on low-end devices | Subtle or no elevation unless the design system specifies |
| `Container` for everything | A `Container` with only padding or only a size hides intent and adds layers | `Padding`, `SizedBox`, `DecoratedBox`: the narrowest widget that does the job |

### Theming

Define the design system once, in `ThemeData`, and read from it everywhere. Never scatter raw values through widgets.

```dart
final lightTheme = ThemeData(
  useMaterial3: true,
  colorScheme: ColorScheme.fromSeed(seedColor: brandColor),
  textTheme: appTextTheme,
  extensions: const [AppSpacing.regular],   // custom tokens via ThemeExtension
);
final darkTheme = ThemeData(
  useMaterial3: true,
  brightness: Brightness.dark,
  colorScheme: ColorScheme.fromSeed(seedColor: brandColor, brightness: Brightness.dark),
  textTheme: appTextTheme,
  extensions: const [AppSpacing.regular],
);
```

- Ship light **and** dark themes; verify both.
- Material or Cupertino is a project-level decision. Follow the project's choice. If the app should feel native on each platform, use adaptive constructors (`Switch.adaptive`, `Slider.adaptive`, `showAdaptiveDialog`) or platform-specific widgets consistently, rather than mixing styles screen by screen.
- Component themes (`FilledButtonThemeData`, `InputDecorationTheme`, `CardThemeData`) belong in the theme, not repeated in each widget.

### Spacing and Layout

Use a consistent spacing scale. Don't invent values:

```dart
// Define once (a ThemeExtension or constants class), reuse everywhere
abstract final class Spacing {
  static const xs = 4.0;
  static const sm = 8.0;
  static const md = 16.0;
  static const lg = 24.0;
  static const xl = 32.0;
}

// Good
Padding(padding: const EdgeInsets.all(Spacing.md), child: child)
SizedBox(height: Spacing.sm)

// Bad
Padding(padding: EdgeInsets.all(13), child: child)   // Not on any scale
SizedBox(height: 23)                                  // Not on any scale
```

### Typography

Use the theme's text roles. Don't set sizes by hand:

```
headlineMedium / titleLarge  → Screen and section titles
titleMedium                  → Subsection titles, list item titles
bodyLarge / bodyMedium       → Default text
bodySmall / labelSmall       → Secondary text, captions
```

- `Theme.of(context).textTheme.titleMedium`, not `TextStyle(fontSize: 17)`.
- Mark screen and section titles with `Semantics(header: true)` so screen readers can navigate by heading.
- **Never clamp or disable text scaling** to make a layout fit. Fix the layout instead (see Adaptive Layout).

### Color

- Use semantic roles from the color scheme: `colorScheme.primary`, `onSurface`, `surfaceContainer`, `error`. Not `Color(0xFF3B82F6)` or `Colors.blue` in widgets.
- Ensure sufficient contrast (4.5:1 for normal text, 3:1 for large text) in **both** themes.
- Don't rely solely on color to convey information (use icons, text, or patterns too).

## Accessibility (WCAG 2.1 AA and Platform Guidelines)

Every screen must work with TalkBack (Android), VoiceOver (iOS), large text, and switch or keyboard navigation.

### Semantics

Flutter builds a semantics tree from your widgets. Standard widgets are mostly accessible by default; custom ones are not.

```dart
// Standard widgets: give them labels
IconButton(
  tooltip: 'Close dialog',           // tooltip becomes the accessible label
  icon: const Icon(Icons.close),
  onPressed: onClose,
)
TextField(decoration: const InputDecoration(labelText: 'Email'))

// Custom tap targets: GestureDetector exposes nothing to screen readers
GestureDetector(onTap: onTap, child: const Icon(Icons.star))      // ✗ Invisible to TalkBack/VoiceOver
Semantics(                                                         // ✓ But prefer InkWell / IconButton
  label: 'Favorite',
  button: true,
  child: GestureDetector(onTap: onTap, child: const Icon(Icons.star)),
)

// Decorative images are noise
Image.asset('assets/divider.png', excludeFromSemantics: true)
// Meaningful images need a label
Image.network(url, semanticLabel: 'Profile photo of ${user.name}')
```

- Group content that reads as one item (a card's title, subtitle, and price) with `MergeSemantics`, so it is announced once instead of as three stops.
- Use `ExcludeSemantics` for purely decorative widgets.
- Mark dynamic status changes (a save confirmation, a validation error) with `Semantics(liveRegion: true)` so they are announced.

### Touch Targets

Interactive elements need at least **48×48 dp** (Material) and **44×44 pt** (Apple HIG). Standard buttons meet this; small custom icons and tightly packed rows often do not. Use `kMinInteractiveDimension`, `IconButton`, or pad the tap area (`InkResponse`, `Padding`) rather than shrinking it.

### Focus and Traversal

```dart
// Dialogs and sheets built with showDialog / showModalBottomSheet manage focus
// and screen-reader scope for you. Prefer them over hand-built overlays.
final confirmed = await showAdaptiveDialog<bool>(
  context: context,
  builder: (context) => AlertDialog.adaptive(
    title: const Text('Delete task?'),
    actions: [
      TextButton(onPressed: () => Navigator.pop(context, false), child: const Text('Cancel')),
      TextButton(onPressed: () => Navigator.pop(context, true), child: const Text('Delete')),
    ],
  ),
);

// Control reading and tab order only when the visual order differs
FocusTraversalGroup(policy: OrderedTraversalPolicy(), child: form)
```

Focus and reading order should match the visual order. External keyboards and switch access users depend on it.

### Text Scaling, Bold Text, and Reduced Motion

- Test at the largest OS font size (200%). Text must wrap or scroll, never clip or overflow.
- Don't put text in fixed-height containers. Use `minHeight` constraints, `Flexible`, `Wrap`, or a scrollable parent.
- Respect `MediaQuery.disableAnimationsOf(context)` for non-essential motion, and `MediaQuery.boldTextOf(context)`.

### Meaningful Empty and Error States

```dart
// Don't show blank screens
class TaskList extends StatelessWidget {
  const TaskList({required this.tasks, required this.onCreate, super.key});

  final List<Task> tasks;
  final VoidCallback onCreate;

  @override
  Widget build(BuildContext context) {
    if (tasks.isEmpty) {
      final theme = Theme.of(context);
      return Center(
        child: Padding(
          padding: const EdgeInsets.all(Spacing.lg),
          child: Column(
            mainAxisSize: MainAxisSize.min,
            children: [
              Icon(Icons.task_alt, size: 48, color: theme.colorScheme.outline),
              const SizedBox(height: Spacing.sm),
              Text('No tasks', style: theme.textTheme.titleMedium),
              const SizedBox(height: Spacing.xs),
              Text('Get started by creating a new task.', style: theme.textTheme.bodyMedium),
              const SizedBox(height: Spacing.md),
              FilledButton(onPressed: onCreate, child: const Text('Create task')),
            ],
          ),
        ),
      );
    }
    return ListView.builder(
      itemCount: tasks.length,
      itemBuilder: (context, i) => TaskItem(/* ... */),
    );
  }
}
```

## Adaptive Layout

Design for the smallest phone first, then adapt up: larger phones, landscape, tablets, foldables, and split-screen. Don't assume portrait or a fixed width.

- `LayoutBuilder` for decisions based on the space a widget was **given**; `MediaQuery.sizeOf(context)` for the window. Prefer `sizeOf`, `viewInsetsOf`, `textScalerOf` over `MediaQuery.of(context)`, so unrelated changes don't trigger rebuilds.
- Use width breakpoints based on window size classes: compact (< 600 dp), medium (600–839 dp), expanded (≥ 840 dp).
- Wrap content in `SafeArea`, and handle the keyboard (`Scaffold` resizes for it; make forms scrollable).
- Prefer flexible layouts (`Expanded`, `Flexible`, `Wrap`, `SliverGridDelegateWithMaxCrossAxisExtent`) over fixed widths and heights.
- Don't lock orientation unless the product requires it.

```dart
LayoutBuilder(
  builder: (context, constraints) {
    // Compact: list. Wider: grid that picks its own column count.
    if (constraints.maxWidth < 600) {
      return ListView.builder(/* ... */);
    }
    return GridView.builder(
      gridDelegate: const SliverGridDelegateWithMaxCrossAxisExtent(
        maxCrossAxisExtent: 320,
        mainAxisSpacing: Spacing.md,
        crossAxisSpacing: Spacing.md,
      ),
      /* ... */
    );
  },
)
```

Test at these sizes (logical dp): 360×640 (small phone), 412×915 (typical phone), 600×960 (small tablet), 840×1200 (large tablet / unfolded), plus landscape and 200% text.

## Loading and Transitions

```dart
// Skeleton loading (not spinners for content)
class TaskListSkeleton extends StatelessWidget {
  const TaskListSkeleton({super.key});

  @override
  Widget build(BuildContext context) {
    return Semantics(
      label: 'Loading tasks',
      child: Column(
        children: List.generate(
          3,
          (_) => const Padding(
            padding: EdgeInsets.symmetric(vertical: Spacing.xs),
            child: SkeletonBar(height: 48),   // one shared shimmer/animation controller
          ),
        ),
      ),
    );
  }
}

// Optimistic updates for perceived speed
Future<void> toggle(String id) async {
  final current = state;
  if (current is! TasksLoaded) return;

  emit(TasksLoaded([
    for (final t in current.tasks) t.id == id ? t.copyWith(done: !t.done) : t,
  ]));

  try {
    await _repository.toggle(id);
  } on Exception {
    emit(current);   // Roll back on failure
  }
}
```

- Prefer implicit animations (`AnimatedContainer`, `AnimatedSwitcher`, `TweenAnimationBuilder`) over hand-rolled `AnimationController`s. Dispose any controller you do create.
- Animate opacity with `FadeTransition` or `AnimatedOpacity`, not by rebuilding an `Opacity` widget.
- Use `RefreshIndicator` for pull-to-refresh on lists backed by remote data.
- Keep platform behavior: default page transitions and scroll physics differ per platform on purpose. Don't override them without a design reason.

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "Accessibility is a nice-to-have" | It's a legal requirement in many jurisdictions (for example the EU's European Accessibility Act) and an engineering quality standard. |
| "We'll make it adaptive later" | Retrofitting adaptive layout, large text, and tablet support is 3x harder than building it from the start, and store guidelines increasingly expect it. |
| "It looks fine on my phone" | Your phone is one size, one font scale, one OS version, one theme. Check small phones, 200% text, dark mode, and both platforms. |
| "The design isn't final, so I'll skip theming" | Use the design system defaults. Hard-coded colors and sizes become permanent. |
| "This is just a prototype" | Prototypes become production code. Build the foundation right. |
| "The AI aesthetic is fine for now" | It signals low quality. Use the project's actual design system from the start. |
| "`setState` is simpler than a Cubit" | For ephemeral UI state, yes. For anything with async work or logic shared across widgets, the Cubit is easier to test and keeps `build()` clean. |
| "A `_buildFoo()` method is easier than a new class" | It can't be `const`, rebuilds with its parent, and can't be tested alone. Extract a widget. |
| "Screen readers will figure out my custom widget" | They only see what `Semantics` exposes. A bare `GestureDetector` is invisible. |

## Red Flags

- Widget files over ~200 lines, or `build()` methods nested more than a few levels deep (split them)
- `_buildX()` helper methods returning widgets instead of widget classes
- Hard-coded colors, `TextStyle` sizes, or magic pixel values instead of theme tokens
- `Colors.deepPurple` and other `flutter create` template defaults left in
- Business logic, API calls, or `Future`s created inside `build()` or directly in widgets
- `setState` at the root of a screen for feature data
- States without value equality, or Cubits that hold `BuildContext` or call other Cubits
- Missing error, loading, or empty states
- `BuildContext` used after an `await` without a `mounted` check
- `GestureDetector` on tappable elements with no `Semantics`, icon-only buttons with no label or tooltip
- Touch targets under 48×48 dp
- Fixed-height containers around text, or text scaling clamped to hide overflow
- Color as the sole indicator of state (red/green without text or icons)
- Only verified on one platform, one screen size, or one theme
- Generic "AI look" (purple gradients, oversized cards, stock layouts)

## Verification

After building UI:

- [ ] `flutter analyze` reports no issues, and the code is formatted (`dart format`)
- [ ] Screen runs on iOS and Android without runtime errors or framework warnings (overflow stripes, disposed-state errors)
- [ ] All interactive elements are reachable and labeled with TalkBack and VoiceOver
- [ ] Touch targets are at least 48×48 dp
- [ ] Layout holds at 360 dp width, tablet width, landscape, and 200% text scale, in light and dark themes
- [ ] Loading, error, and empty states all handled
- [ ] Follows the project's design system (theme tokens, spacing scale, typography roles)
- [ ] State lives in Cubits/Blocs with immutable, equatable states; `build()` has no side effects
- [ ] Widget tests cover the states, and accessibility guidelines are asserted where it matters (`meetsGuideline(androidTapTargetGuideline)`, `labeledTapTargetGuideline`, `textContrastGuideline`)
